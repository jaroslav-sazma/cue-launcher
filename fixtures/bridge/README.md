# Bridge test vectors

Shared test vectors of the Cue: bridge protocol. The normative specification is
`docs/bridge-protocol.md` in the Cue: launcher's repository; it describes what each file contains,
and this file records where the values come from. Both implementations run their contract tests
against these files. The launcher's repository holds the canonical copy of this directory, which its
Kotlin tests read in place. The Bridge repository keeps a copy of the JSON files, refreshed by its
`tools/sync-vectors.sh`; its Swift tests read that copy and, while the launcher's repository is
checked out beside it, fail on any JSON file that differs from the canonical one. Change the vectors
in the launcher's repository only.

## Provenance

| File | Source |
|---|---|
| `chacha20poly1305.json` | Copied from RFC 8439 §2.8.2 and Appendix A.5 |
| `x25519.json` | Copied from RFC 7748 §5.2 and §6.1 |
| `hkdf.json` | Copied from RFC 5869 Appendix A.1 to A.3 |
| `pairing.json` | Generated by the launcher's Kotlin implementation (cases), computed by a throwaway Python script (commitments) and written by hand (commitment checks, ceremonies, abort reasons, low-order keys) |
| `frames.json` | Generated by the launcher's Kotlin implementation (frames) and written by hand (the seqs accepted before each rejection, the replay window cases) |
| `messages.json` | Generated by the launcher's Kotlin implementation (examples) and written by hand (streams) |
| `state-sync.json` | Written by hand from the diff rule of `active-set`; checked by the Bridge repository's Swift tests |
| `filters.json` | Written by hand from the phone's filter rules; the importance values are those of Android's `NotificationManager` |
| `l2cap.json` | Generated by a throwaway CryptoKit script; checked by the launcher's Kotlin contract tests |

The RFC files anchor the primitives: an implementation that passes them computes ChaCha20-Poly1305,
X25519 and HKDF-SHA256 correctly. Every generated value was cross-checked by a second, independent
implementation, and the Swift side MUST still recompute every generated value itself rather than
copy anything from the Kotlin code; that recomputation is the cross-check between the two
implementations.

The inputs of the generated values:

- **Pairing cases.** The first uses the RFC 7748 §6.1 key pairs, Alice's as the Mac's and Bob's as
  the phone's, and the fingerprints of the two test certificates in `pairing.json`, self-signed EC
  P-256 certificates made with OpenSSL for these vectors only. The second repeats the first with the
  two fingerprints swapped. The third derives its private keys as SHA-256 of
  `cue-bridge/vector/mac/14` and `cue-bridge/vector/phone/14`, and its fingerprints as SHA-256 of
  `cue-bridge/vector/fingerprint/mac` and `cue-bridge/vector/fingerprint/phone`; index 14 is the
  first one whose SAS has a leading zero.
- **Commitment checks, ceremonies and abort reasons** are built from the pairing cases: every key,
  proof, SAS and `K_ble` in them is a case's. Each implementation runs the ceremonies whose `checks`
  name its side, as the honest party against the other side's messages.
- **Low-order keys** are the encodings of the X25519 points of order 1, 2, 4 and 8, canonical and
  non-canonical; each yields the all-zero shared secret.
- **`frames.json`** seals every frame with the `K_ble` of the first pairing case.
- **`l2cap.json` derivations.** The first uses the RFC 7748 §6.1 key pairs, Bob's as the phone's and
  Alice's as the Mac's, under the `K_ble` of the first pairing case; the second swaps which pair
  plays the phone; the third repeats the first under the `K_ble` of the third pairing case. The
  low-order case pairs Bob's key with the Mac key u = 0 of the low-order keys in `pairing.json`.
- **`l2cap.json` records.** The seals and failures use the record keys of the first derivation case.
  The largest plaintext is not spelled out: it is 16384 bytes where byte i has the value i mod 256,
  and the vector gives the size, the first 18 bytes, the tag and the SHA-256 of its record. The
  failure with a declared length of 16401 bytes is the two length bytes followed by `zeroFill` zero
  bytes, so that a reader that skips the length check fails it on the AEAD instead.
- **`l2cap.json` transcript.** Its ephemeral private keys are SHA-256 of
  `cue-bridge/vector/l2cap/phone` and `cue-bridge/vector/l2cap/mac`, under the `K_ble` of the first
  pairing case. The phone's second frame, an empty `active-set`, is cut after its first 10 bytes,
  and the rest shares a record with a `bye` frame.

Every private key in these files is public test material and must never be used for anything else.

## Changing a vector

A vector changes together with the specification and the codec, under the change policy of the
specification: an additive vector keeps `bridgeProtocolVersion`, a changed expected value means a
breaking change. Regenerated values are committed as JSON only; the generator is not kept.
